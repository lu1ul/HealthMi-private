# 快捷指令快速排队与详细同步结果设计

日期：2026-11-24

状态：已实施并通过 iOS 16 远程编译，待真机验证快捷指令后台调度

## 1. 背景与目标

当前「同步健康数据」App Intent 在 `perform()` 内直接执行完整同步。一次调用会初始化 Core Data、读取 Keychain、建立小米会话、拉取最多九类数据、写入 HealthKit、保存游标并刷新摘要；快捷指令必须一直等待这条链路结束。链路超时或帮助进程被系统终止时，快捷指令只能显示「无法与帮助程序通信」，用户无法知道是凭据、网络、HealthKit、数据库还是某一类数据失败。

本次改造保留静默执行，目标是：

- 快捷指令在短时间内完成“请求排队”，不等待完整同步；
- 排队失败时立即返回具体原因；
- 后台同步保存运行级状态和每类数据的详细错误；
- 后台同步完成后发送详细本地通知；
- 提供「查询最近同步状态」快捷指令动作，读取已排队、运行中、成功、部分失败或失败的完整结果；
- 保留现有前台同步、BGAppRefresh、HealthKit 写入和同步历史行为。

## 2. 目标与非目标

### 目标

1. `SyncHealthDataIntent` 只负责校验前置条件、创建运行记录并提交后台刷新请求。
2. 运行记录至少保存运行 ID、触发来源、时间、状态、每类数据结果、错误域、错误码和描述。
3. 后台任务开始和完成时更新同一运行记录；任务取消或数据库准备失败也要留下明确结果。
4. 详细错误使用稳定的本地结构保存，避免只依赖短暂的 `AppModel.lastError`。
5. 旧版 Core Data 数据库可以继续打开；本次尽量不引入必须手工迁移的存储结构。

### 非目标

- 不保证 iOS 会立即启动 BGAppRefresh；系统仍会根据后台资源策略决定实际启动时间。
- 不把后台稍后发生的错误回写到已经完成的快捷指令动作；快捷指令动作通过运行 ID、通知和查询动作获得结果。
- 不修改小米 API 协议、HealthKit 数据映射或同步游标语义。
- 不重新启用 `openAppWhenRun`，保持静默执行。

## 3. 方案对比

### 方案 A：快捷指令直接等待完整同步

保留当前实现，只增加错误捕获和错误文本。

- 优点：调用结束时可以直接返回最终结果。
- 缺点：仍受 App Intent 帮助进程和系统执行预算限制；完整同步超时后仍可能出现「无法与帮助程序通信」。不符合静默自动化的可靠性目标。

### 方案 B：快速排队 + 持久化运行结果（采用）

快捷指令只做前置检查、写入排队记录和提交 `BGAppRefreshTaskRequest`，随后立即返回。后台任务负责完整同步，并持久化运行状态和详细错误；新增查询状态动作和详细本地通知。

- 优点：快捷指令动作短、可预测；后台错误可按数据类型定位；不要求打开 App；不会把“已排队”误报为“已完成”。
- 代价：快捷指令返回时同步尚未完成；BGTask 的实际启动时间由系统决定，最终结果需要通过通知或查询动作取得。

### 方案 C：增加专用 App Extension 或 XPC 帮助进程

把同步放入独立进程并由快捷指令调用。

- 优点：可以单独管理进程生命周期。
- 缺点：iOS 后台执行、HealthKit、Keychain、工程目标和签名配置复杂度显著增加；当前项目没有 extension 目标，超出本问题所需范围。

## 4. 选定方案的实现设计

### 4.1 运行记录

新增 `SyncRunRecord` 和 `SyncRunStore`，以 `UserDefaults` 保存最近若干次运行的 Codable JSON。采用现有应用容器，不改变已有 Core Data 模型，降低 iOS 16 用户升级时的迁移风险。

状态枚举：

- `queued`：已创建运行记录并成功提交后台请求；
- `running`：后台任务已领取该运行；
- `succeeded`：所有启用类型完成；
- `partialFailure`：至少一个类型成功、至少一个类型失败；
- `failed`：前置检查失败或所有类型失败；
- `cancelled`：后台任务在完成前被系统取消。

每类结果保存：类型、拉取数量、新增数量、是否成功、错误域、错误码、错误描述。运行记录同时保存汇总文本和失败类型列表。

### 4.2 快捷指令排队

`SyncHealthDataIntent.perform()` 的步骤：

1. 准备共享数据库并执行凭据/HealthKit 可用性检查；
2. 如果已有排队或运行中的记录，返回原运行 ID和当前状态；
3. 创建新的 `queued` 运行记录；
4. 提交最早约一秒后的 `BGAppRefreshTaskRequest`；
5. 如果提交失败，将该运行记录标为 `failed` 并返回调度错误域、错误码和描述；
6. 成功时立即返回“已排队”、运行 ID和排队时间。

`perform()` 不再创建完整同步 Task，也不再使用 55 秒 watchdog。

### 4.2.1 真机崩溃后的安全收敛

iOS 16.3 真机执行首版快速排队后仍出现“无法与帮助程序通信”，再次运行时提示 App 意外退出。Apple 要求所有 BGTask handler 在应用启动完成前注册；App Intent 帮助进程不保证经历同样完整的启动路径。

因此 `perform()` 已进一步收敛为只写 `UserDefaults` 队列。Keychain、HealthKit 和 Core Data 检查全部移到后台执行，失败会写入运行记录。只有当前进程确认 `BGTaskScheduler.register` 返回成功时才提交立即调度；未确认注册时保留“已排队”，由 App 启动时已经提交的周期后台请求领取。

### 4.3 后台任务

BGTask 处理器启动时先重新安排下一次周期刷新，然后领取现有 `queued` 运行；若没有手动排队记录，则为周期刷新创建新的 `background` 运行。同步过程中按类型更新运行记录，结束时根据结果写入最终状态。

### 4.4 详细错误

错误记录保留：

- 错误域，例如 `HKErrorDomain`、`MiAPI`、`HTTP`、`Keychain`或系统 `NSError` 域；
- 错误码，例如 HealthKit code、HTTP 状态码、小米 API code、Keychain OSStatus；
- 面向用户的中文描述；
- 对应的数据类型。

前台界面继续显示现有错误；后台通知显示运行 ID、最终状态、成功类型、失败类型及各失败类型的详细错误。快捷指令新增「查询最近同步状态」，可在同步稍后执行后读取相同内容。

### 4.5 兼容性与并发

- 不改变外部 API；`syncAll` 仅增加可选运行 ID和返回摘要的内部参数。
- 继续使用现有跨实例同步互斥锁，防止前台、BGTask 和快捷指令重复同步。
- 运行状态写入在 `@MainActor` 上串行执行；状态记录采用有限历史，避免 UserDefaults 无限增长。
- 运行中进程被终止后，下一次排队请求会把超时的旧运行标为失败并允许重试。

## 5. 验收标准

1. 快捷指令动作在不打开 App 的情况下快速返回“已排队”和运行 ID。
2. 已有活动运行时不会重复启动，并返回已有运行状态。
3. 数据库、凭据或 BGTask 提交失败时，动作返回具体错误，而不是通用帮助程序错误。
4. 后台同步完成后，运行记录可查询；网络、登录、HealthKit、Keychain、数据库和单类数据错误均保留域、码和描述。
5. 混合成功/失败时状态为 `partialFailure`，通知和查询结果列出成功与失败类型。
6. 后台任务取消、重启或旧运行卡住时，状态不会永久伪装为成功。
7. iOS 16 目标代码不依赖 iOS 17 专用 API；现有 Core Data 和迁移逻辑保持可用。
